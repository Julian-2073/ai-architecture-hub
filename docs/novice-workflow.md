# 从不懂技术的描述到可实施方案

目标：用户表达想完成的事和期望效果，Codex负责技术理解、必要澄清、条件性选型与实施。用户无需先知道组件名，也无需学会填写本文件的JSON。

## 在对话中怎样工作

1. 先用一句自然语言复述用户的目标，识别用户、操作、输入、效果与验收。用户说“插件”“数字孪生”时，先理解要放在哪里、完成什么；不要直接把名词当技术规格。
2. 运行 `discover '用户的描述' --json`，有现成项目时加 `--project 已核实的绝对路径`。读取候选的职责、实现路径和相关失败经验。匹配只是线索，用户明确说“不做”的能力不要加入。
3. 表述未命中或匹配不合理时，用当前Codex的理解继续拆解；按能力词 search 或读取场景ID/标题。用下面的有引用解释调用 discover，让解释与记录连接；不要只要求用户换关键词、报技术名或填写架构术语。
4. 把已知约束、推断、待确认事项分开。工具的问题列表只是候选，先剔除用户已经说明的事项。仅询问最多两个会实质改变路径的问题，优先业务问题；先问模型/数据从哪里来，比要求小白提供仓库路径更有帮助。只有确实要接入且路径不可发现时才询问路径。
5. 读取 implementation_paths。它给出输入、动作、交付、验收与回退；检查实际项目和可调用工具，明确哪些阶段能执行、哪些缺素材/权限/环境。存在多种运行技术时选一种适合项目的路线，不能把候选全装上。
6. 讨论任务给出条件性推荐及原因即可；实施任务在授权范围内继续落地、测试和审查。运行、构建与业务效果分别验收，保留失败和环境限制，再将有证据的经验回写。

对用户解释“为什么这样构建、代价是什么、改了什么条件会换方案”；专业术语放在需要解释的时候，而非作为用户输入门槛。

## Codex有引用的理解

优先使用 `--intent-json` 直接传JSON，只读任务也无需创建临时文件；可写任务也支持 `--intent 文件路径`。两者互斥。输入由Codex整理，不让用户填写。

原话：“让买家绕着商品瞧瞧，看看背后和底下的样子”。Codex可解释为产品空间查看，仍需确认是否真要交互三维：

```json
{
  "schema_version": 1,
  "goals": [
    {
      "scenario_id": "scenario-interactive-3d",
      "source_quote": "绕着商品瞧瞧，看看背后和底下的样子",
      "certainty": "inferred"
    }
  ],
  "excluded_scenarios": [],
  "known_constraints": [],
  "open_questions": ["希望客户自己转动查看，还是播放预先拍好的展示？", "已有产品模型或照片素材吗？"]
}
```

`goals`最多10项，每项场景ID必须存在、source_quote必须逐字出现在本次完整需求里，certainty只能是explicit或inferred。inferred产生待确认项，不能冒充已知事实。排除项以相同scenario_id/source_quote格式登记在excluded_scenarios；与目标冲突会拒绝。

`known_constraints`最多12项，格式为name/value/source_quote。name可选platform、assets、data_source、interaction、deployment、budget、scale、privacy、persistence；每项需原话依据。不要把“可能在网页用”写成用户已确认web。无法归类的条件保留在交接解释中，不强塞字段。

`open_questions`最多两个。工具检查引用存在、字段和冲突，不检查“这句原话在语义上是否支持该场景”；该责任属于Codex及对话确认。它不调用额外模型，不是一个新增的语义模型服务。

查找场景时先按你理解的能力词运行 `search '空间查看' --kind scenario --json`；必要时只读取data/discovery-profiles.json中的ID与title，不默认加载全库正文。

## 已编制的五类路径

| 用户想完成的事 | 路径 | 当前边界 |
|---|---|---|
| 让客户旋转查看、换色或观察产品 | 产品三维展示 | 资产制作与浏览器运行分开；新项目未验证 |
| 点击企业或设备对象查看状态 | 企业/设备状态映射 | 不自动假定三维；无真实接口时明确演示性质 |
| 拖动节点并查看或编排关系 | 关系与流程画布 | 模板未运行；流程执行器需要单独实现 |
| 上传企业资料并问答、看出处 | 企业资料问答 | 解析、授权、引用与撤销各自验收；模板未运行 |
| 给机器与人员排任务 | 资源排程 | 先建立简单规则和约束，再判断是否需要求解器 |

路径元数据：data/implementation-paths.json；可阅读正文：knowledge/templates/template-path-*.md。它们是实施配方，不是已接通全部软件的插件集合。

## 工具可调用性

`discover ... --check-environment`仅检查python3/node/blender的PATH和标准应用位置，不启动程序，不读取用户资料。找到可执行文件不证明版本、插件或授权可用；找不到不证明全机没有安装。

实际实施时，Codex还需检查当前会话中可用的专用工具或连接器、项目调用位置和依赖；先读对应工具说明，再判断实际调用方式。没有可用接口时如实列缺口，不把技术卡片当成已经安装的工具。

## 成熟度与验收

“匹配到候选”“有步骤的模板”“存在某项目的局部成功参考”“本次项目实际验收通过”是四种状态。参考记录的版本、数据性质、设备和限制不能被新项目继承为成功结果。

本次重点检查不含技术名的需求、含混名词、否定要求、同意图不同说法、有引用的Codex解释、路径前提和证据边界。测试集合上的命中不能换算成通用需求理解准确率。
