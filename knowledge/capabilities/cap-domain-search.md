## 四类常见业务问题，不必从引擎名开始

| 用户怎么说 | 先明确什么 | 推荐起点与升级条件 |
|---|---|---|
| 按客户编号/订单号找一条记录 | 精确身份、字段、范围和权限 | 先复用业务API/数据库索引；不要把精确编号交给相似度结果猜测 |
| 在商品目录里输入几个词并筛选 | 中文、型号/别名、排序和筛选体验 | 先测现有全文能力；不足时在Meilisearch、Elasticsearch/OpenSearch等相同职责路径中收束候选 |
| 不记得原文，换种说法也想找到资料 | 关键词基线失败在哪里，允许哪些模型/数据处理 | 有证据再评估向量或混合检索；已有PostgreSQL可比较pgvector，专用服务有收益时比较Qdrant |
| 沿供应商、客户或设备关系查几层 | 哪种关系、有效时间、路径深度与来源 | 先验证关系表/SQL；关键多跳负载超出时再比较Neo4j。只画图无需自动上图数据库 |

### 三条可比较的组合路线

1. **现有数据库与业务接口**：字段筛选或库内全文足够时推荐复用。应用承担授权、分页和回读；保留简单恢复与查询契约。
2. **业务库+检索投影**：确需独立检索能力时选择合适方法/引擎。新增同步、失败重试、删除/撤权和重建成本；先指定唯一事实来源。
3. **带依据的语义/混合检索**：词法基线不足才引入嵌入、可能的向量与重排。先核查现有引擎是否已覆盖，避免职责重复的多库。回答生成属于下游另一步，不是搜索成功的必然结果。

图路径查询是另一种查询语义，按上表单独比较；不要将全文、向量、关系图当成同一种工具直接排名。

### 模块与数据合同

用户查询+可信身份 → 查询解析/精确匹配分流 → 授权范围内检索 → 必要的排序/重排 → 记录ID与来源/版本 → 业务详情回读。

写入端：主记录提交 → 有版本的变更/删除事件 → 幂等索引更新 → 可见性确认；失败保留状态和可重放游标。

- 索引保存稳定ID、资料/租户范围、源版本与更新信息；每条结果可回到原记录。
- 权限在可信服务层落实，摘要、高亮、总数、聚合、缓存和图路径也按同一范围处理。
- 源记录保存成功、索引任务接收和用户可搜到是三个时点；承诺多快生效需实际观察。
- 向量分数不是事实正确性或权限概率；近似检索还需检验过滤后的召回。

### 给Coding的实施顺序与验收

先检查现有接口/库/部署→收集有代表性的查询与正确结果→建立现有基线→对会改变选择的缺口比较两三条路径→定义权限、变更与删除合同→在授权内接入并回读业务结果。

验收覆盖精确ID、中文/别名、无答案、错词、不同权限、修改/撤回与删除、重建/重复事件。先确定相关性、可接受延迟与资源标准，不虚构通用准确率。数量增加不是引入向量库或集群的充分理由。
