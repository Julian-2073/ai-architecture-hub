# TanStack Query

> 服务端状态管理库 · 表单、状态与数据网格 · 候选，尚无本项目采用结论。

[返回索引](../../docs/technology-catalog.md) · [能力地图](../capabilities/cap-software-map.md) · [选型判断](../../docs/technology-selection.md)

## 它解决什么

管理异步数据获取、缓存与失效。官方资料入口供复核基本定位；以下适用性、接入和验证内容是选型建议，不是全部经过实测的产品承诺。

## 何时选，何时不选

- **适用条件**：多页面重复请求或异步状态较多。
- **职责边界**：不替代后端数据正确性与访问控制。
- **选择分界**：反复请求、失效和异步状态复杂时可减少手写逻辑；租户和身份必须进入正确缓存边界。
- **比较入口**：原生请求加简单缓存；其他查询库。先比较同层能力；不同层只能作为组合，不能因为名称都叫平台就直接替换。
- **相邻卡片**：[React Hook Form](tech-react-hook-form.md)、[Zustand](tech-zustand.md)、[TanStack Table](tech-tanstack-table.md)、[AG Grid](tech-ag-grid.md)。同域不等于等价，不必同时引入。

## 最小验证与验收重点

**决定性验证**：验证租户切换、过期数据和并发更新。

## 录入、修改与保存的具体分工

官方概述把它定位为获取、缓存、同步与更新server state的工具，区分本地客户端状态和远端数据生命周期。

- **何时增加**：多个页面重复取数、刷新失效和异步状态有明显维护负担时评估；简单请求已足够则不新增缓存框架。
- **相邻层边界**：查询缓存不是后端事实来源，也不是数据库备份。刷新结果不能自动解决多人同时修改的覆盖、对象权限或事务问题。
- **接入顺序**：把会改变结果的筛选、分页、企业/身份等条件放在正确查询边界；保存成功后按业务契约刷新或更新相关查询。采用乐观显示时另定义失败回滚和冲突处理。
- **可观察验收**：验证账号/企业/筛选切换不读旧范围，保存后列表与详情一致；失败不永久保留未确认结果，重试策略不能制造重复业务写入。
- **长期代价**：缓存键、失效范围、SSR与持久化（若使用）、异常恢复；组件减少手写状态，但不能免除一致性设计。
