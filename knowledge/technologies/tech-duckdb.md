## 它解决什么

以 SQL 分析本地表格与列式文件。官方资料入口供复核基本定位；以下适用性、接入和验证内容是选型建议，不是全部经过实测的产品承诺。

## 何时选，何时不选

- **适用条件**：CSV、Parquet 和本地分析任务。
- **职责边界**：不把它直接等同多用户事务型数据库。
- **选择分界**：适合分析型 SQL 与文件查询；不要把本地分析成功推断成多用户在线事务系统适配。
- **比较入口**：pandas；PostgreSQL。先比较同层能力；不同层只能作为组合，不能因为名称都叫平台就直接替换。
- **相邻卡片**：[pandas](tech-pandas.md)、[Polars](tech-polars.md)、[ClickHouse](tech-clickhouse.md)、[dbt（版本与发行线需区分）](tech-dbt.md)。同域不等于等价，不必同时引入。

## 业务分界：分析历史数据与在线填报分别判断

“打开销售文件计算分组汇总”可以评估嵌入式分析路线；“多位员工持续修改同一笔订单”应先复用业务事务库，再判断是否需要独立分析层。无需因为数据量增加就默认同时安装两个数据库。

官方并发说明区分：进程内模式下，一个进程读写或多个进程只读；同一写进程可以有多个写线程，同一行的冲突修改可能失败。不能把“支持多个线程”当成任意多个应用进程可直接同时写原生数据库文件。

当前读取的官方页面另介绍Quack远程协议和DuckLake路线，并包含成熟度/发布时间自述；这些是不同部署或格式条件，未在本库验证。也不能用旧的绝对说法断言DuckDB没有任何多进程路径。采用前核查目标版本、部署方式及实际维护状态。

- **具体接口**：SQL、文件路径/表与连接配置 → 聚合结果、结果表或导出数据；输入文件本身仍需单独管理权限、版本和保留。
- **决定性问题**：输入快照是否固定？运行在一个任务进程还是多个应用实例？文件来自本地还是远端？扫描和中间结果资源由谁承担？
- **验收草案**：对真实文件类型核对空值、日期、去重和汇总口径；按代表性数据量测峰值内存、临时磁盘与耗时；涉及并发就按实际进程模型检查冲突和重试。
- **切换保留**：源文件及版本、SQL、类型与口径、输出契约和调度信息；不要只留不可重建的分析结果。
