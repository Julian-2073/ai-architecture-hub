# Auth.js

> Web 认证工具。历史或特定情境候选；新项目须核查官方后继路线。

## 用户想完成什么

为 Web 应用组织登录、会话和身份提供商接入。定位来自官方资料；下面的情境判断、组合和验证是作者建议。

## 什么时候考虑

已有受支持 Web 框架且需要应用内认证。先检查当前项目和平台已有能力；同一技术在不同业务条件下可以有不同采用决定。

## 选择分界与组合

认证与业务授权分开；先比较现有框架认证，不为简单登录默认自建身份服务器。

应用内认证、集中身份服务与业务授权分开；先复用现有身份与框架，不将登录当权限完整实现。

## 接入前提

- 核实具体产品/发行版/版本、依赖与锁文件；HEAD和网页示例不是应直接采用的稳定配置。
- 重点检查：当前依赖、框架、运行时、数据与部署约束。
- 明确数据来源、对象权限、错误与恢复、维护人及可导出格式；官方能力不自动补齐业务规则。

## 会改变选择的验证

验证会话失效、回调、跨站与对象授权。事先确定代表性数据、目标环境、通过标准与停止条件；目前没有本项目PoC、集成或运行通过证据。

## 成本、维护与退出

适配器与框架升级；保留稳定业务用户ID和账号映射。接入人力、固定运行、按量与维护分别计算；商业模块、服务、模型、字体和素材条款分别核查。未知价格和规模不估金额。

维护判断需结合支持政策、变更和安全信息；本次只记录正文中明确的具体提示，不凭热度决定成熟度。

## 已读到的官方提示

当日官方README说明 Auth.js 已加入 Better Auth，并建议新项目先考虑该后继路线，特定功能例外需明确。此处保留既有项目入口，不把它当无条件新项目默认；后继路线需另做适配和许可核查。
